# Security Policy

## What this project is

Automotive Retail Performance Intelligence (ARPI) is a **public portfolio
repository**. It is not a product and it is not deployed.

To be precise about the threat model:

- There is **no production system**, no hosted instance, and no service anyone
  can log in to.
- There are **no users**, no accounts, and no authentication surface.
- There is **no real data**. Every row is generated by a deterministic synthetic
  data generator that lives in this repository. There is no customer data, no
  employee data, no dealership data, and no personally identifiable information
  of any kind. The dealer group, its three stores, and every transaction in the
  dataset are fictional.
- There is **no external service dependency** at build time. Continuous
  integration runs with zero repository secrets configured and never contacts a
  hosted database, a cloud account, or Power BI Service.

The realistic risk here is therefore narrow: a credential from a contributor's
*local* development environment being committed by accident, or a dependency
with a known vulnerability being pulled in. Everything below is aimed at those
two things.

See [PRIVACY_AND_ETHICS.md](PRIVACY_AND_ETHICS.md) for the data-ethics position,
including why the data is synthetic and what that means for any conclusion drawn
from it.

## Supported versions

| Version | Branch | Supported |
|---|---|---|
| `0.1.x` | `main` | Yes — the only supported line |
| Anything older | — | No |

Only the current `main` branch receives fixes. There are no maintenance
branches, no backports, and no long-term-support releases.

## Reporting a vulnerability

**For a non-sensitive finding** — an outdated dependency, a hardened default
worth adopting, a documentation error about security — open a normal
[GitHub issue](https://github.com/mpalmer79/Automotive-Retail-Performance-Intelligence/issues).
Public discussion is fine and preferred for these.

**For anything sensitive** — a credential you found in the repository or its
history, or any finding that should not be public before it is fixed — use
**GitHub private vulnerability reporting**: go to the repository's *Security*
tab and choose *Report a vulnerability*. This opens a private channel visible
only to the maintainer.

Do not disclose a sensitive finding in a public issue, a pull request, a commit
message, or a discussion thread.

No email address is published here on purpose. GitHub's private reporting
channel is authenticated, is auditable, and does not create an address for
scrapers.

### What to expect

This is a portfolio project maintained by one person in their spare time.
Expectations are set accordingly, and honestly:

- **Acknowledgement:** best-effort, typically within a week.
- **Assessment and fix:** best-effort, prioritised by real impact. Given that
  there is no deployment and no real data, most findings will be low severity.
- **Credit:** happily given in the fix commit or release notes if you want it.
- **No bounty**, no service-level agreement, and no guaranteed response time.

If a report goes unanswered for a month, a polite nudge on the same thread is
welcome.

## Secret handling policy

The rules, in the order they matter:

1. **Credentials live in environment variables.** Nothing else is a supported
   way to supply one.
2. **`.env` is gitignored** and must stay that way. `.gitignore` ignores `.env`
   and every `.env.*` variant, with a single explicit negation for
   `.env.example`.
3. **`.env.example` is the template.** It contains placeholder values only. A
   real password must never appear in it.
4. **`ARPI_DATABASE__PASSWORD` never appears in YAML, in SQL, or in Python
   source.** Configuration profiles under `config/` define the database host,
   port, name, user, and SSL mode — never the password. The password is read
   from the `ARPI_DATABASE__PASSWORD` environment variable, with `PGPASSWORD` as
   a fallback.
5. **Logs redact secrets.** The configuration object's string and repr forms
   render the password as `***REDACTED***`, and the logging layer redacts
   connection URIs and `*password*=value` assignments before a record is
   emitted. Debug logging is not an exemption.
6. **CI carries no secrets.** The only credential in
   `.github/workflows/ci.yml` is the password of a throwaway PostgreSQL service
   container that exists for the lifetime of a single job and is reachable only
   from that job. It is written as a literal deliberately: storing it as a
   repository secret would falsely imply it protects something, and would stop
   the workflow from running on forks.

## Database role model

The SQL layer uses three roles with distinct privileges. Least privilege is the
point; a reporting tool has no business being able to write.

| Role | Purpose | Privileges |
|---|---|---|
| `arpi_admin` | Owns the schemas and runs DDL | Full control over all ARPI schemas |
| `arpi_loader` | Pipeline writes | Read and write on `raw`, `staging`, `warehouse`, and `audit`; no DDL |
| `arpi_reporter` | Power BI, Excel, ad-hoc analysis | **Read-only**, and **no access to the `raw` schema at all** |

`arpi_reporter` is the credential that would realistically be shared with a
reporting tool, so it is the most constrained: it can read the curated
`reporting` views and the dimensional model, and it cannot see the raw landing
layer, cannot write anything, and cannot alter anything.

Never run the pipeline, or connect a report, as a database superuser.

## Automated controls, and their limits

These controls exist. None of them is sufficient on its own, and it is worth
being explicit about what each one misses.

| Control | What it does | What it does **not** do |
|---|---|---|
| `.gitignore` rules | Keeps `.env`, virtualenvs, dumps, and generated datasets out of the index | Nothing if a file is force-added with `git add -f`, and nothing about history |
| `scripts/check_secrets.py` | Fails CI on a tracked `.env`, connection URIs with an inline password, AWS keys, private key blocks, GitHub tokens, `sk-` keys, JWTs, and quoted credential assignments | Not entropy-based, does not scan git history, does not understand context, and will miss any credential that does not match its handful of patterns |
| `detect-private-key` pre-commit hook | Blocks a commit containing a private key block | Only runs if the contributor installed pre-commit, which is optional |
| CI `repository-checks` job | Runs the naming, documentation-link, and secret checks on every push and pull request | Only sees the tree at that commit, not what was already merged |
| GitHub secret scanning | Detects provider-recognised credential formats and can revoke some of them | Only covers formats GitHub knows about |

**`scripts/check_secrets.py` is a safety net, not a secret scanner.** Treat a
clean run as "no obvious mistake was found", never as "there are no secrets
here". Read its module docstring before relying on it for anything.

## If a credential is committed by accident

Do these in order. The order is the important part.

1. **Rotate the credential immediately.** Before you touch git. Change the
   database password, revoke the token, delete the key. Assume the moment it
   reached a public repository it was harvested — treating rotation as optional
   because "it was only pushed for a minute" is how this goes wrong.
2. **Confirm the rotation worked.** The old credential must no longer
   authenticate.
3. **Then** remove it from the tree, and from history if it was pushed. Removing
   it from `HEAD` alone is not enough; a public commit remains reachable. Use
   `git filter-repo` (or the GitHub-documented equivalent) to rewrite history,
   then force-push, and ask GitHub Support to expire cached views of the old
   objects if the repository is public.
4. **Add a control so it cannot recur.** A `.gitignore` entry, a pattern in
   `scripts/check_secrets.py`, or both. A fix without a control is a fix that
   happens again.
5. **Note what happened** in the pull request or commit body — not the
   credential, the lesson.

Scrubbing history *before* rotating is the common mistake, and it is the wrong
order: it delays rotation while doing nothing about the copy that was already
cloned.

## Dependencies

Runtime dependencies are deliberately few — pydantic, pydantic-settings, PyYAML,
pandas, and optionally psycopg — and are declared in `pyproject.toml` with lower
bounds. There is no web framework, no ORM, and no CLI framework in the
dependency tree, which keeps the attack surface and the upgrade burden small.

Report a known-vulnerable dependency as a normal GitHub issue; it is not
sensitive information.
